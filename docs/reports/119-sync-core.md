# 119 Device-to-device sync (core, folder backend, Wi-Fi pairing, Sync screen)

## 1. Summary
Vela can keep two devices' local data in step through a shared folder (Syncthing, Dropbox, Nextcloud, Google Drive clients...). Each device writes one AES-256-GCM encrypted file; merging is last-writer-wins per item with tombstones, so there is no server, locking or conflict file. New Settings > "Sync between devices" screen: a 3-step first-time setup (folder, sync code, what to sync) and a status/devices/options screen afterwards. Synced: subscriptions + notify level + groups, playlists + Watch later, watch history (latest watch per video), blocklist, syncable settings and Look colors. Not yet: WebDAV, Dropbox/Drive APIs, LAN peer-to-peer, login transfer (later phases of the plan).

## 4. Decisions the spec didn't dictate
- State-diff instead of hooks: each domain flattens to `key -> value`; changes are found against the last sync. Playlists and groups are matched by name (ids differ per device); renaming one therefore looks like delete + create.
- History is one record per video (latest watch), timestamped by when it was watched, so a late-found old watch cannot beat a newer one; capped at 10 000 videos.
- Playlist order is not synced (each device appends); item values never include position, so no ping-pong.
- Settings: schema keys plus Look colors/fonts only. Layout (density, text size, bars), downloads, account, notifications, region, paths and sign-in stay per device.
- Only the LOCAL account's data syncs; Google-account data is re-read from YouTube on each device.
- Safety: a sync that would delete >10 items and >50% of what it knows is refused; a wrong code publishes nothing; tombstones expire after 90 days.
- The sync code is stored through the secret store (Keystore / libsecret), never in backups; "Sign out everywhere" does not delete it.
- Code is 16 characters (about 80 bits), generated by the app; a typed code ignores case, spaces and dashes.

## 5. Known issues / unverified assumptions
- Not run on Android: the SAF folder (create, write with `"wt"`, rename quirk after `createFile`) and the sync on app stop (Android may freeze the process before it finishes; the next start syncs anyway). SAF writes are not atomic; a reader that catches a half file fails the integrity check and retries next sync.
- No background schedule on Android (no WorkManager job yet): sync runs at start, every 10 min while the app is open, and ~2 s after leaving it.
- Cloud clients may create "conflicted copy" files; they are read as extra device files (harmless: older data loses).
- Clock skew: last-writer-wins trusts device clocks; a device with a clock far in the future wins every conflict.
- Settings and groups changed by a sync show on screens the next time they are opened (no live refresh of every screen).
- Changing the code requires turning sync off and setting it up again on every device (old files stay unreadable and are skipped).
- The sync state row grows with history (about 1-2 MB at 10 000 videos); moving it to its own table is a later optimization.
- Logins are not synced. Plan: a one-time encrypted "transfer login" (phase 4), not continuous cookie sync.

- Fixed after first device test: both devices stuck on "Syncing". Cause: the setup screen's coroutine scope was cancelled when the screen switched to the status screen mid-sync, and the cancelled sync left the status on "Syncing". `SyncService.syncNow` now runs in the service's own scope (a screen leaving cannot cancel it) and resets the status if cancelled. This also explained the earlier full-suite test hang.

## 6. Manual test checklist
1. PC: Settings > Sync between devices. Step 1 "Choose folder": pick a folder your sync app shares (a "Vela sync" sub-folder is created). Step 2 "This is my first device": note the code. Step 3 leave all on. "Start syncing": status shows "Up to date".
2. Phone: install the same build, open Settings > Sync between devices, Step 1: choose the same shared folder (wait until your sync app has delivered the PC's file). Step 2 "I already have a code": type the PC's code. "Start syncing".
3. Confirm subscriptions, groups, playlists, Watch later, blocklist and history from the PC now appear on the phone ("Sync now" if not).
4. Subscribe to a channel and add a playlist video on the phone, wait for your sync app, "Sync now" on the PC: they appear. Remove one on the PC, sync both: it disappears on the phone.
5. Watch a video halfway on one device, sync both: the other resumes from that position.
6. Enter a wrong code on a third setup: you get "The code does not match" and nothing is added to the folder.
7. Settings > Sync > "Sync code" shows the code; "Turn off sync on this device" keeps your data.

## 7. Addendum: same-Wi-Fi sync (added after the first device test)
- Why: the folder mode needs a separate sync app to move files; without one the devices never saw each other (each only had its own file).
- New module `:sync-lan` (pure JVM, `LanSyncTransport`): every ~4 s each device broadcasts UDP (port 47321) "group (a hash of the sync code), device id, HTTP port, file version, name". A device that sees a same-group peer whose version changed downloads its file (`GET /f/<id>.vsync` with the group in a header; a device only serves its own file) into a local cache folder and syncs. The engine merges from the cache, so a peer that is switched off still contributes its last file. Files stay AES-GCM encrypted on the wire.
- The engine no longer rewrites its file when nothing changed (30-minute heartbeat), otherwise two devices would trigger each other forever. Covered by a test that waits and checks the file is byte-identical.
- Setup step 1 is now "How should your devices connect?": Same Wi-Fi (default) or A shared folder. Tests: `LanSyncTest` (2 real DBs over loopback UDP/HTTP converge and settle; a different code is ignored), `SyncUiTest.wifiIsTheDefaultAndNeedsNoFolder`.
- Linux pickers (sync folder, cookie file, download folder, backup open) use the GTK dialog through `zenity` with fallback to the Java dialogs.
- Limits: both apps must be open (Android may stop the listener when the app is in the background); Wi-Fi "client isolation" (guest networks, some routers) blocks it; no firewall prompt handled (Fedora Workstation's default zone allows high ports; stricter zones would block incoming connections); broadcast reception on Android needs the multicast lock (held only while sync is on), not tested on a real device.
- Manual test: on both devices turn sync off if it is on (Settings > Sync > Turn off), then Settings > Sync > keep "Same Wi-Fi" > this is my first device > Start syncing on one; on the other "I already have a code" and type it. Both on the same Wi-Fi with Vela open: within about 10 s each shows "On this Wi-Fi now" for the other, and data crosses.

## 8. Addendum: accounts (sign-in) and per-account data
- Finding: the PC was signed in to a Google account, so its subscriptions/groups/history/playlists belonged to that account, while sync only moved the local profile. The phone (local profile) had nothing in common.
- Now every Google account on a device syncs its own data under `a/<accountId>/...` (account ids are stable hashes of the channel/e-mail, so two devices agree on them); the local profile keeps the short keys.
- New option "Google sign-in" (OFF by default, with a warning): shares each signed-in account (identity + cookies) inside the encrypted file (`AccountsDomain`). A device adopts an account only if it has none with that id or it needs a new sign-in; a device already signed in keeps its own session (avoids two devices fighting over rotating cookies). The first Google account on a device becomes its active account. Removing an account on a device makes it declined there (sync won't bring it back); sign-ins are never removed from another device.
- Engine fix needed for this: a domain that appears later (the account just adopted) no longer causes its already-known records to be treated as local deletions (`seenLocal` bookkeeping); covered by `SyncServiceTest.aSignedInAccountMovesToTheOtherDeviceWithItsOwnData`.
- Risks, unverified with a real account: YouTube may invalidate or flag a session used from two devices/IPs; the shared snapshot is not refreshed when the owner's cookies rotate (a stale snapshot only matters when a device needs a new sign-in); cookies sit in the secret store (Keystore/libsecret) and, encrypted, in the sync folder/cache.
- Manual test: Sync > What is synced > turn on "Google sign-in" on BOTH devices, Sync now on both; the phone should show the PC's account in the profile menu with the account's subscriptions.

## 9. Addendum: near-live sync
- While the app is open, `SyncService.checkForChanges()` runs every 15 s: it fingerprints everything that would be synced (cheap, order independent) and, when it differs from after the last sync, syncs about 1.5 s later (at most once per 20 s, so a playing video's position updates do not sync constantly). A full sync still runs every 10 minutes and on Android when leaving the app. Over Wi-Fi the other device fetches within ~4 s. Expected delay for a change to appear on the other device: about 10-25 s while both apps are open.
- Cost: every 15 s the app reads the synced tables once (history is capped at 10 000 videos); not measured on the phone.
- The status card says "Ready to sync" until the first sync finishes (it said "Up to date" too early).
- Test: `SyncServiceTest.aLocalChangeIsNoticedAndPublishedWithoutAManualSync`.
