## Stage C: Android account playback and age-restricted videos (the centrepiece)
Goal: an age-restricted video plays on Android for a signed-in (age-verified) account through the governor, last in the tier order. Measurement first, then implement the winner, with a stop rule.
- Facts already established (task 16 feasibility read): NewPipeExtractor's PoTokenProvider hook is used only for its Android/iOS clients, whose tokens come from DroidGuard/iosGuard and cannot be minted outside the real apps; a WebView BotGuard token only helps web-family clients; yt-dlp has no built-in provider; our own /player with cookies on WEB/MWEB/TVHTML5 returned UNPLAYABLE in task 13 WITHOUT tokens or a correct web context.
- Spike A (own web-client path): WEB/MWEB /player with cookies + SAPISIDHASH + visitorData + PO token from a BotGuard WebView (implement `PoTokenProvider` for Android: hidden WebView, cached with expiry, refreshed ahead, never blocks UI, failure = unavailable) + stream URL deciphering (n/signature) reusing NewPipeExtractor's player-JS machinery if its API allows. Success = a real GET with Range returns 206 for one video and one audio stream of the age-restricted test video HtVdAasjOgU, run ON THE DEVICE, using the test account (VELA_TEST_COOKIES imported on the phone, or an explicit debug import) and only through the governor.
- Spike B (yt-dlp on Android): run yt-dlp (pure Python) inside the app via an embedded Python runtime (e.g. Chaquopy; check its current licence/terms and Gradle/AGP compatibility with this project's AGP 9.x and Kotlin versions before investing), with a JavaScript runtime for the player challenges (yt-dlp supports deno, node, bun, quickjs as external executables: evaluate shipping a quickjs executable as a native library in the APK's native lib dir and invoking it from yt-dlp, or an in-process alternative), cookies via the governor-owned temp file, the same updater/rollback design as Linux (download the yt-dlp release, verify SHA2-256SUMS, atomic swap, canary, rollback). Success = same criterion as Spike A on the device. If B works it ALSO gives Android a yt-dlp tier 4 for anonymous failures (parity with Linux), which is a major reliability gain: measure both uses.
- Measure for each spike on the device: success on the age-restricted video and on 5 normal videos, resolve latency (cold and warm), APK size delta, memory, startup impact, update path, how often it will need maintenance, and how well it fits the governor. Put the comparison table in the report. Do not guess: if a number was not measured, write "not measured".
- Implement the winner as the Android account tier (and as anonymous yt-dlp tier if B), registered in the data-driven tier order (account last), diagnostics labels distinct, governor budgets applied, health canary updated, friendly failure kept for when it is unavailable. If neither spike works on the device after a serious attempt, STOP: write exactly what was tried, errors and numbers, leave the existing friendly failure, and make sure nothing half-built is registered.
