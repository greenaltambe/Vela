# Task 14: reliability hardening and account safety

Follow CLAUDE.md (report docs/reports/14-reliability.md; terminal reply max 5 lines + anything the owner must do). Read docs/SPEC.md section 4 and docs/reports/13-accounts.md (especially Known issues and measurements). Build in stages, commit nothing, record unfinished stages in the report.

Purpose: (1) make the fallback chain survive YouTube changes and blocks, (2) make it as unlikely as we can that a signed-in Google account gets flagged or banned, (3) find breakage early. Reference behaviour (Grayjay's YouTube plugin config, verified): login features default OFF except "login fallback" (used only when login is required: bot check, age restriction); "provide YouTube activity" (reporting what you watched via the authenticated client) is OFF by default; it generates PO/BotGuard tokens itself, has aggressive recovery from IP changes, a captcha flow that stores the GOOGLE_ABUSE_EXEMPTION cookie, rate-limits subscription fetching, and updates its YouTube logic without an app release. Anything not measured by you is an assumption: say so.

## A. Account Safety Governor (common code, single choke point)
- ALL traffic that carries account credentials (innertube-auth calls, yt-dlp --cookies calls, sync, future writes/reporting) must go through one `AccountGovernor` per account. No code path may attach credentials any other way (enforce structurally: credentials only injectable through the governor-owned transport).
- Budgets (settings in schema, sane defaults): authenticated playback resolves per hour (default 20), browse/sync calls per minute, writes per hour; minimum spacing with jitter; strict serialisation per account; one global kill switch.
- Circuit breaker per account: CLOSED / OPEN(cooldown) / HALF_OPEN. Opens on: HTTP 429, captcha or /sorry redirect, "unusual traffic" text, repeated LOGIN_REQUIRED after a previously valid session, account-verification / "confirm it's you" pages, cookie invalidation, and yt-dlp stderr equivalents (list the patterns; mark which you observed vs assumed). Cooldowns escalate (1 h, 6 h, 24 h) and reset after sustained success. While OPEN: no authenticated call is made, the chain skips tier 2 with the reason "account cooling down until HH:MM", and the UI shows a banner with a plain explanation and a deliberate "try now" action (confirmation required).
- Policy settings (schema, Settings > Account): `account.useFor` = NEVER / ONLY_ON_FAILURE (default) / ALWAYS (extends the existing accountFallbackMode, keep one source of truth), `account.reportActivity` (default OFF), `account.useForChannels` and `account.useForDetails` (default OFF), `account.downloadsMayUseAccount` (default OFF: downloads use anonymous tiers; the account is used only when the user allows it and anonymous failed).
- Strictly anonymous operations (assert in tests): search, trending, channel pages, RSS feed refresh, comments, SponsorBlock/DeArrow/RYD calls, stream-URL fetches from googlevideo, thumbnails, update checks. 
- Credential-leak audit test: instrument every HTTP transport (OkHttp, NewPipe downloader, yt-dlp invocations incl. its -v request log, WebView sign-in) and run every user flow with a fake account carrying marker cookies; assert the markers appear only on allow-listed hosts (accounts.google.com, www.youtube.com, youtubei.googleapis.com, music/studio only if used) and only for allow-listed operations; never on third-party APIs, googlevideo, image hosts or logs. Run the same against real yt-dlp with the test cookies (VELA_TEST_COOKIES) using its verbose log to list every host it contacts with cookies; report them.
- Consistent identity: per account persist and reuse visitorData, user agent, client name/version and device id; do not randomise per call; refresh only on explicit staleness/failure. Keep Android and Linux identities distinct per account but stable.
- Onboarding gate when adding a Google account: short plain-language screen (third-party clients violate YouTube's terms; a throwaway account is strongly recommended; what the app will and will not send; how to remove everything) with explicit acknowledgements, then the policy defaults above, then the `reportActivity` choice shown explicitly (default off).
- Local audit log of every authenticated request (time, kind, host, result, governor decision), redacted, viewable in Diagnostics > Account activity, capped and purgeable. This is how the owner sees exactly what the account did.
- NEEDS_RELOGIN: banner on every screen (not only Accounts), periodic lightweight `checkSession` (rate-limited by the governor) at app start and daily, never signing out on network errors.

## B. Fault-injection ("chaos") test harness
- Wrappers for Extractor/transport/HttpTransport/ProcessRunner that inject: 403 page, 429, /sorry redirect, LOGIN_REQUIRED, UNPLAYABLE, expired stream URLs mid-playback, offline, slow/throttled bodies, truncated bodies, malformed JSON, and process timeouts; scriptable per tier and per call.
- A scenario table (data-driven) asserting for each: which tiers are tried and in what order, TierMemory contents, governor/breaker state, diagnostics lines, user-visible result, and that credentials were/weren't used. Include: anonymous blocked then account then alt then yt-dlp; account breaker opens and stays open; breaker closes after cooldown with a fake clock; account switching mid-failure; ALWAYS/NEVER modes; downloads never touching the account by default; PlaybackSession recovery on mid-playback 403 and on network change. Runs in allTests.

## C. PO tokens
- Implement `PoTokenProvider`: (1) Android: BotGuard in a hidden WebView (session/visitor-bound and per-video tokens as needed), cached with expiry, refreshed ahead of expiry, never blocking UI, failure = provider unavailable (no crash, diagnostics line). Compile-only here: say so and give manual steps. (2) Linux: evaluate a BotGuard provider run with the system node (the bgutil-ytdlp-pot-provider approach) both for yt-dlp (plugin mode) and for our alt-client tier; measure, do not guess.
- MEASURE (put matrices in the report): which client profiles (WEB, MWEB, TVHTML5, ANDROID_VR, IOS, ANDROID) become playable with a token, anonymous and with the test account; whether IOS/ANDROID streams still return 206 without a token today; add a regression canary for that so we learn the day it stops.
- If a profile becomes viable with tokens, enable it in innertube-profiles.json behind the provider being available.

## E. Health, self-healing and updates
- `ExtractorHealth`: canary matrix (search, videoInfo, streams for 3 stable reference videos incl. a music and a short; per tier; one 206 GET each) run on demand, at app start if the last run is older than 7 days, and periodically (Android WorkManager, network constraint; Linux timer thread). Persist results; Diagnostics > Health shows per-tier status with last success, last failure reason and history. A canary that detects streamingData with no plain URLs (SABR/UMP-only) must say so explicitly ("YouTube may have moved this client to SABR") — detection only, no implementation.
- Remote config for logic that changes often: client profiles, client versions, disabled-profile kill switches, canary video ids. Signed JSON (Ed25519), monotonic version, size cap, HTTPS only, offline fallback to the bundled copy, URL in a setting (default empty = bundled only), a `scripts/sign-remote-config` tool plus docs on how to host it (e.g. a file in a GitHub repo). Verification failure = ignore + diagnostics line. Unit-test tampering, rollback, expiry.
- yt-dlp updates (Linux): detect version and age; offer an app-managed copy in the data dir (download the official release asset, verify against the published SHA2-256SUMS, atomic replace, keep the previous version for rollback) and/or `yt-dlp -U` for self-managed installs; setting `ytdlp.autoUpdate` (OFF / ASK default / AUTO); run the health canary after an update and roll back if the yt-dlp tier regressed.
- NewPipeExtractor staleness: record the version and its release date in code; Diagnostics warns after 60 days and says how to bump; add `scripts/bump-newpipe.sh` (updates the catalog, runs offline + live tests, prints a verdict).

## F. More failure modes
- Captcha/"/sorry": detect and surface as Blocked(captcha) distinct from a plain block; Android: WebView solve flow storing the exemption cookie and injecting it into anonymous requests as Grayjay does, evaluate whether it helps (you probably cannot reproduce a challenge on demand: implement defensively, test with fakes, label unverified).
- Network handoff (Wi-Fi to mobile, VPN change): PlaybackSession re-resolves and resumes, bounded; verify with the chaos harness; expose the cause in Diagnostics.
- Slow-stream failover: if throughput stays below the stream bitrate for N seconds while buffering, re-resolve through the chain preferring a different tier/profile once (bounded, setting, default on), resuming at the current position.
- Anonymous request pacing: a global limiter for extractor calls (max concurrent, minimum spacing for bursts like feed refresh and search paging) so one IP does not look like a scraper; measure that normal use is not slowed noticeably.
